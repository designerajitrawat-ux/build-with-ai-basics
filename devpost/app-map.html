Make it pop: app map

A short guide to where things live in this project, so you know where to start when you want to change something.

What the app is

Make It Pop runs fully in the browser. You paste a client's feedback (or add a WhatsApp screenshot), press Decode, and a second screen walks the round: Ask the client (vague points, each with a clarifying question), Ready to do (clear tasks to tick off) and Report back (a message or PDF for the client). There is no server and no AI service inside the app.

It has four main pieces:

  • js/phrases.js: the hand-made library of vague phrases, question templates, the wording of the questions message and the report, and the two text samples.
  • js/decoder.js: the logic. It turns raw text into items. It has no page code, so the tests in tests/decoder.test.js load it directly with Node.
  • js/app.js: the page. It reads the text box, calls the decoder, switches between the two screens, draws the lists and runs the two sheets (send questions, report).
  • js/screenshot.js: reads WhatsApp screenshots on the device with Tesseract.js, then hands the recognised lines to chatFromScreenshot in the decoder.

One action, followed through the code

The action: you press Decode on "Can you make it pop, it looks too plain right now." and see it in Ask the client with "make it pop" highlighted and a question under it.

Reference route: three stops, in the order the code runs. Search for the anchor text in your editor to jump there.

  1. The click: js/app.js, search for function runDecode

    The Decode button is wired to runDecode. It passes the text box value to the decoder, keeps the result in state.items, picks up the client's name, calls render and switches to the round screen with showScreen.

  2. The decision: js/decoder.js, search for function decode and function findVague

    decode splits the text into points with splitPoints. For each point, findVague checks it against every phrase group built from KINDS in js/phrases.js. If anything matches, the point becomes an "ask" item and buildQuestion fills the matching template with the client's own words, in English and in Hinglish. Otherwise it is a "ready" item with a tag from tagTask.

    render splits the items into the two lists, writes the title and chips (to ask, ready, clarity score), the three round steps (renderRound) and the progress line. renderAskItem draws the kind label, the client's text with the matched words wrapped in highlight marks (built by highlighted, never with raw HTML), the question and the "Mark as clear" button.

To change this, start here

  • Add a vague phrase (for example a new Hinglish word): add it to the right group inside KINDS in js/phrases.js, then add a line to a test in tests/decoder.test.js and run node --test.
  • Change a question's wording: edit the en or hi template of that group in KINDS. {phrase} is replaced with the client's words.
  • Change "big but subtle" style detection: the loud and quiet word lists in CONTRADICTION in js/phrases.js.
  • Change the questions message greeting or thanks: MESSAGE in js/phrases.js; the message itself is assembled by buildMessage in js/decoder.js.
  • Change the report's wording: REPORT in js/phrases.js. The message is written by buildReport in js/decoder.js; the PDF layout is buildReportDoc in js/app.js plus the .doc styles and the print rules in styles.css.
  • Change how screenshots are cleaned (which bubbles are kept, how times are removed): chatFromScreenshot and TIME_AT_END in js/decoder.js. The tests use real recognised lines saved in tests/fixtures/.
  • Change the samples: SAMPLES in js/phrases.js, and samples/whatsapp-chat.png for the screenshot sample. Some tests count the sample points, so update them too.
  • Change colors or fonts: the variables at the top of styles.css.
  • Change what a click does (tick, move, send, report, new feedback): handleListAction, openSendSheet, openReportSheet and startOver in js/app.js.

A practice to reuse

Test with real messages, then turn every surprise into a test. During the build, a realistic line, Menu me "Contact" add karo, was read as English because it had only one Hinglish marker word. The fix (a short line with one marker counts as Hinglish) is recorded under Revisions in devpost/checklist.md, and the test "Hinglish points get Hinglish questions and English points get English questions" in tests/decoder.test.js now guards it. The same happened with false alarms: "pop-up" and "plain white background" are now in a test that checks they are not flagged.

On your next project: before calling a feature done, try it with a few inputs copied from real life, and write each one that breaks as a small test. The fix stays fixed, and the test explains why the rule exists.

Run it again

  • Open index.html in any modern browser. Nothing to install.
  • Or serve the folder: npx serve . and open the printed address.
  • Run the checks: node --test (Node.js 20 or newer).
